# 项目分类目录

`data/schemes/site/scheme.json` 是本站分类（体系编号 `site`）的目录：15 个一级领域、74 个二级分类（另有每个领域一个「其他」扩展位），外加一组「形态」。本文说明它为什么这样设计、怎样归类、怎样扩展，以及它经过怎样的检验。文件格式见 [data-model.md](data-model.md)，分类结果怎样放入见 [operations.md](operations.md#分类体系)；页面上还可以切换到别人做好的公开分类，见 [schemes.md](schemes.md)。

## 设计原则

1. **两个互相独立的维度。** 主分类回答“它服务于什么领域”，形态回答“它是什么样的东西”（应用、命令行工具、库与 SDK、框架、服务与平台、运行时与引擎、智能体、智能体技能、插件与扩展、模型、数据集、教程与课程、资源清单、规范与文档、研究实现、配置与模板、硬件与实物）。用一棵树同时表达两者会使节点成倍增加：几百个“智能体技能”会全部堆进同一个节点，而它们的主题（营销、设计、安全、科研……）才是用户区分它们的依据。分开以后，营销技能是「营销与增长」加形态「智能体技能」。
2. **按服务的领域归类，不按技术手段归类。** “用了 AI”不是领域。只有当项目本身就是智能体或模型的底层设施时，才归「智能体基础设施」或「模型与算法」。
3. **一级覆盖整个软件世界，二级在项目密集的地方细分。** 目录最初依据创建不足一年的 361 个项目归纳，那批项目高度集中在智能体生态；如果只照它们设计，通用软件就会留白。所以一级领域按通用软件的版图划分，智能体相关的二级分类可以更细。
4. **编号稳定。** 节点编号一旦被分类结果引用就不再改变，改名只改 `label`；拆分、合并节点时先迁移结果，`validate` 会检查所有引用。
5. **每个一级领域有一个「其他」。** 明确属于该领域、但没有合适子类的项目放进去，它既是安全阀，也是扩展的信号（见下）。

## 归类规则

- **一个项目一个主分类，最多补充 2 个关联分类。** 项目确实同时属于另一个领域时才写关联分类，不要为了稳妥而多写。
- **智能体相关的边界**（最容易混淆，按顺序判断）：专为写代码的归「编程智能体」；运行在已有编程智能体之上、管理多个会话的面板归「编程智能体的管理与协作」；面向个人长期对话的助手归「个人助手」；以上都不是的通用底座才归「运行时与编排」。
- **技能包看主题。** 有明确单一主题的技能包归它服务的领域；没有特定主题的通用集合、厂商或平台官方的技能集合、技能管理工具归「技能与提示词库」。
- **围绕代码库的索引与图谱**归「代码理解与评审」，对话与任务的记忆归「记忆与上下文」。
- **学习材料**（课程、教程、书籍与文章，含收集这类材料的清单）主分类归「课程与教程」，所讲的主题记为关联分类。跨领域的 awesome 导航归「综合资源清单」；有明确主题的清单按主题领域归类，形态标为资源清单。
- **设计与前端**：视觉与交互设计的方法、技能、规范归「设计与界面」；能直接使用的组件和渲染库归「前端与界面开发」。

## 怎样扩展

- **增加二级分类。** 某个领域的「其他」累积到约 10 个项目、并且能看出共同主题时，拆出新的子类，把这些项目移过去，并在 `guidance` 里写清收录与排除范围。拆之前先看相邻子类的 `excludes` 是否需要补一句，避免新旧节点抢项目。
- **增加一级领域。** 只有当相当数量的项目放不进任何一级领域、且它们构成一个独立的、不依赖某种技术手段的领域时才增加。不要为某个技术（比如“AI”“区块链”）单开一级领域，它们应分散在各自服务的领域里。
- **增加形态。** 形态是平铺的列表，直接在 `forms` 里加一项；不需要改动任何主分类。
- **合并或删除节点。** 先把引用它的分类结果迁到别的节点，再从目录里删掉，`validate` 会报出仍然指向已删除节点的结果。
- **更新 `note`。** 目录或结果的来源、覆盖范围、可信度变化时同步修改，页面会原样展示。

## 检验

目录是否“有足够的区分度”和“不只适用于建它的那批项目”，用盲评检验：让互相独立、只看到项目名称、描述、话题和目录的评审，各自给项目分类，并如实标注有没有把握（明确 / 有竞争节点 / 无处可放）。

| 样本 | 数量 | 结果 |
|---|---|---|
| 创建不足一年的项目（建目录所用） | 361 | 初版目录下：明确归类 73%，放入「其他」1%，无处可放 1 个 |
| 同一批中 80 个，由另一位评审独立再分类 | 80 | 二级分类完全一致 91%，一级领域一致 94%，形态一致 99% |
| 早于一年创建的项目，随机抽样 | 100 | 初版目录下：明确归类 50%，放入「其他」12%。据此补了后端、图形、通用库、规范、容器、防护、素材、机器学习框架 8 个节点并收紧若干边界规则 |
| 另一批随机抽样的早期项目（修订后的新样本） | 100 | 补节点后：明确归类 69%，放入「其他」6%。据此再补编程语言、电商 2 个节点和代理的收录范围 |
| 又一批随机抽样的早期项目（没有参与任何一次修订） | 100 | 最终目录：明确归类 70%，放入「其他」1%，无处可放 0 个 |
| 前面那 91 个新项目，用修订后的目录重新分类 | 91 | 明确归类从 60% 升到 75%，与上一次的二级分类一致 90%（说明修订没有打乱原有归类） |

最后一批里仍有的缺口各只出现一次：操作系统核心组件（如 init 与服务管理）、家居安防与监控、无线感知。按上面的规则，它们暂不单独加节点，作为观察项，同类项目积累起来再拆。

读这些数字时请注意：

- 评审是语言模型，不是人。**一致性高说明规则可复现，不等于分类正确**；目录和任何分类结果都没有经过人工验证，也没有测过准确率。
- 「有竞争节点」多数是项目本身兼具两种性质（比如既是编程智能体又是编排底座），这是主分类加关联分类的设计所允许的，不一定是目录的缺陷。
- 创建不足一年的项目集中在智能体生态，较早的项目则以通用软件为主，两批的分布差别很大，所以单独看任何一批的比例都不能代表整个总榜。
