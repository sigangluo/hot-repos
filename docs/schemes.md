# 分类体系

看板可以按多套分类体系给项目分类，页面上用筛选面板顶部的下拉框切换。一个分类体系回答“这些项目分别属于什么类”，每套体系说明了**谁分的、怎么分的、分了哪些项目**。

不同体系互相独立，不做映射：同一个项目在不同体系里的位置可以完全不同，详情里会并排显示，方便对照。

## 两种体系

- **本站分类（`site`）**：本站自己定的领域分类，由语言模型判断，有一二级分类、关联分类和项目形态，设计见 [taxonomy.md](taxonomy.md)。语言模型判断没有经过人工验证，可能有错。
- **外部体系**：别人已经做好的公开分类。我们**不重新标注**，只保存“总榜里的哪个项目属于来源里的哪个类”这一事实，并注明出处、许可与取得日期。分类的名称沿用来源的原文。

## 新旧与维护

每个体系都有**创建**和**最近更新**两个日期（`scheme.json` 的 `created`、`updated`，含义见 [data-model.md](data-model.md)），页面在体系下拉框下面一行直接显示，并注明距今多久；超过 1 年没有更新会明说。2026-11-10 的情况：

| 体系 | 创建 | 最近更新 |
|---|---|---|
| 本站分类 | 2026-11-10 | 2026-11-10 |
| GitHub Explore 主题合集 | 2017-09-16 | 2026-09-25 |
| Awesome 清单 | 2013-11-14 | 2026-11-09 |
| Wikidata 软件类型 | 2012-10-29 | 2026-11-10 |
| OSS Insight 开源项目合集 | 2022-01-19 | 2026-05-07 |
| Borges 等的人工分类 | 2017-06-08 | 2020-01-24 |
| CNCF Cloud Native Landscape | 2016-11-04 | 2026-11-10 |
| LF AI & Data Landscape | 2018-11-26 | 2026-10-28 |

“最近更新”是来源里相关内容最近一次变化，不是我们取回数据的日期（后者是 `as_of`，“关于这个体系”里的“取得于”）。Borges 的数据集 2020 年之后没有变过，页面会标出“已超过 1 年没有更新”。Awesome 清单的体系日期取各清单里最早创建的和最近推送的；每个清单自己的创建与最近推送日期写在它的分类说明里（分类右侧的 ⓘ），可以看出这个清单还有没有人维护。Wikidata 的创建日期取它上线的日期，最近更新取这批条目里最近一次被编辑的时间，几乎每天都在变。

使用时要知道的：

- **每个体系只收录一部分项目**。没被收录不代表项目不属于那一类，只是该体系没有分到它；页面显示每个体系的覆盖数，没被收录的项目在该体系下没有分类，按分类筛选时不会出现。
- **Awesome 清单是总榜自己的内容**：总榜里有两百多个 Awesome 类仓库（名字含 awesome，或话题含 awesome / awesome-list），每个是有人围绕一个主题收集的项目清单，README 里按章节分组，本身就是一份人工做的分类。我们直接取这些 README：清单是分类，章节是子分类，清单收录的项目属于对应章节。清单本身太多（一百三十多个），所以按 Awesome 总索引（[sindresorhus/awesome](https://github.com/sindresorhus/awesome)）的领域分组（编程语言、前端、安全、数据库……）归到一级；总索引没收录的清单（约六成，多是较新的 AI 智能体、技能、MCP、大模型类清单）归在“其他（总索引未收录）”组，不是本站另外判断的。章节由标题层级自动解析（取最能分出像样章节的那一级，并过滤目录、贡献说明、相关清单等），个别结构特殊的清单可能分得不准；总榜里收录不足 3 个项目的清单不保留。清单收录不等于质量保证，一个项目可以出现在很多清单里。
- **“人工策展”不是“互斥分类”**。Explore 与 OSS Insight 的合集是围绕主题挑选项目，收录有取舍、一个项目可以在多个合集里，个别合集的成员也不一定贴合名称（比如 Explore 里的“Made in Colombia”收了 FastAPI），我们照来源原样保存。
- **Borges 的数据是 2017 年 1 月的**：只覆盖当年已经很热门、且至今仍用同一名称的项目，近年的项目基本不在其中；六个领域划分较粗，把“形态”（库、工具、文档）和“领域”混在一起。
- **两份 Landscape 侧重云原生与 AI / 数据基础设施**，对总榜整体的覆盖面有限；一个项目出现在多个子类别时，第一个作为主分类，其余作为关联分类。

## 许可与署名

每个外部体系的出处、许可和署名写在它的 `scheme.json` 的 `source` 里，页面在“关于这个体系”和详情的分类卡片里原样显示。仓库里只保存“项目属于哪些类”的事实和分类名称，不转存来源的其他内容（Landscape 里的 Crunchbase 数据与 logo、合集页面的图片都不要）。

## 同步

```bash
uv run hot-repos schemes sync              # 全部外部体系
uv run hot-repos schemes sync borges cncf  # 只同步指定的
```

流程：取来源（`awesome` 需要总榜里各清单的位置，从 `data/repos.parquet` 读）→ 按项目名对上今天的总榜（忽略大小写，改名过的项目按 `manifest.json` 的 `aliases` 对到当前名称）→ 去掉没被用到的分类 → 校验 → 写入 `data/schemes/<编号>/`。任何一步失败，该体系已有数据保持原样，其余体系不受影响，命令以非零状态退出；来源取不到任何一个匹配的项目时视为格式变了，同样拒绝写入。除取得日期外没有变化时不重写文件。

总榜更新（`fetch`）后再同步一次，新进总榜的项目才会出现在外部体系里；定时同步见 [deployment.md](deployment.md)。

没有对上的主要原因：来源里的项目已不在总榜（Star 不够或已删除），或项目改过名而总榜没有记录旧名。

## 新增一个外部体系

1. 确认来源的许可允许这样使用（记录项目与分类的对应关系并注明出处），并记下许可标识与署名要求。
2. 在 `src/hot_repos/sources/` 加一个模块，提供 `collect(fetcher) -> Collected`：返回体系定义（名称、简介、`method`、`primary`、`source`、`nodes`，字段见 [data-model.md](data-model.md)；创建与最近更新日期用 `sources.dated()` 补上，GitHub 来源可用 `Fetcher.github_dates()` 取）和“来源里的 `owner/repo` → 节点编号列表”。解析写成不访问网络的纯函数，便于用小段样本测试。
3. 在 `sources/__init__.py` 的 `registry()` 里登记，键就是体系编号；设置 `order` 决定页面里的排列。
4. 运行 `uv run hot-repos schemes sync <编号>`，再 `validate` 和 `export`，在页面里看一遍。

## 没有接入的

逐个查证后没有接入，原因是没有可直接复用的项目标注，或和总榜的重合太少（不是说它们没有价值）：

- **Ecosyste.ms OSS Taxonomy**：有六个维度的词表，但只有词条，没有给具体项目打好的标注。
- **GitRanking**：301 个应用领域的词表，来自 GitHub 话题。最终的领域清单没有以能直接取用的形式发布，数据集里是话题的标注（三位标注者）和排序，带项目标签的文件有 1GB 量级；它的话题本来就是仓库作者填的，已经是筛选里的“话题”分组。
- **GitHub 话题**：仓库作者自己填的标签，已经是筛选里的“话题”分组。
- **Apache 软件基金会项目清单**（projects.apache.org）：数据里多数项目没有 GitHub 仓库地址，与总榜只对上 10 个。
- **LF AI 之外的 Linux Foundation 全景图**（17 个子全景图）：与总榜的重合最多 52 个、多数不到 20 个，不值得各占一个体系；总的 Linux Foundation 全景图（96 个项目）试接过，但它的分类只有一个“Projects › All”，没有分类信息，已移除。
- **更多的 Awesome 清单**：这里只取了总榜里的 Awesome 仓库；总榜之外还有几千个清单（如 awesome.ecosyste.ms 收录的），接入要上千次请求，可以以后再做。
- **PyPI Trove 分类、publiccode.yml**：前者只覆盖 Python 包，后者由各项目自己声明、采用面很窄。
